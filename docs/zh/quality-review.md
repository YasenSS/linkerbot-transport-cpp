## 已确认的运行时失败

安装后消费者在进入 `main()` 后发生内存分配失败时，异常可能逃逸到程序边界，导致进程
终止，而不是返回消费者通常的失败结果。受控 ARM64 Linux 复现在修复前以状态 134
退出；修复后输出错误说明，并以状态 1 退出。

这是验证程序的可靠性缺陷。该复现不意味着所有使用此库的应用都会发生相同失败，
也不需要 CAN 硬件。修复将消费者主体移入 `run_consumer()`，在 `main()` 中捕获
`std::exception`，同时保留既有的成功及显式失败返回值。

永久回归测试 `transport-consumer-allocation-failure` 在 Linux 的 GNU 或 Clang 构建中运行。
链接器包装在进入 `main()` 后的第一次分配处注入失败；之后的分配交给真实分配器，
包括 sanitizer 的分配钩子。测试要求状态 1、错误说明，以及没有成功消息；进程中止不能
算作通过。正常安装后消费者测试仍独立保留。

## 契约与误报

析构函数有意关闭当前类拥有的资源。显式限定这些调用的类名，保留了 C++ 在析构期间
原本就采用的分派行为。`CANBusLease` 的移动赋值有意允许关闭失败在两个 owner 改变前
抛出；`noexcept(false)` 明确表达这一既有契约。若将其改为不抛异常，反而会使调用方
失去重试机会，并不是正确修复。

FakeTransport 的错误设置函数原本就会保存指定错误。针对性运行探针核对三个设置函数，
包括使用长消息替换已有消息。显式构造 optional 中的值，使 Cppcheck 能识别该操作；
编译期检查确认此处默认分配器的 `std::string` 移动构造和移动赋值不抛异常。

测试中的断言继续保留。`tests/optional_value.hpp` 提供
`test_support::require_value()`：通过普通 `if` 检查是否有值，空值时抛出异常，并按值
返回所含对象，而非返回指向 optional 内部的引用。因此调用命名或临时 optional 时，
不会留下指向已销毁 optional 存储的引用。
辅助函数本身仍在分析输入中，并未绕过未检查取值规则。

厂商 ABI 声明，以及故意测试非法状态、移后状态的用例保持不变。诊断与这些必要行为冲突
时，在相应声明或断言处注明准确的规则及原因。局部注释不会对其他文件关闭规则，
也不改变报告评分；相关契约仍由运行测试验证。

## Catch2 分析模型

Cppcheck 2.13 无法解析 Catch2 3.8 宏实现中的 token 拼接字符串字面量。
`validation/catch2-cppcheck.cfg` 为项目使用的公开宏建立模型。它仅供 Cppcheck 使用；
正常构建和测试仍使用真实的 Catch2 头文件及运行库。

模型保留断言操作数和测试体，区分不同测试用例与 section，并区分失败后终止的断言和
失败后继续的检查。`validation/test-cppcheck-model.py` 使用 **29 个静态哨兵用例**和
**两个运行探针**验证模型：一个使用真实 Catch2，另一个使用模型。静态用例要求检出
故意设置的空指针及越界错误，包括后续测试用例和 section 中的错误。运行探针核对异常
类型不匹配时，fatal 断言会终止当前测试，nonfatal 检查会继续执行，并确认 section 名称
表达式会被求值。另有注册参数检查，只接受 TEST_CASE 名称和标签的字符串字面量；
动态注册表达式必须先扩展模型，不能静默跳过分析。

这些检查覆盖项目当前使用的建模结构，不意味着模型与 Catch2 的所有功能完全等价。
未知宏、预处理失败及其他分析失败仍属于错误。模型检查命令和分析范围见
[构建指南](build.md#c-report-card)。
